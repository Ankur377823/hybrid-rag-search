# Contributing to rag-hybrid-search

Thank you for contributing to `rag-hybrid-search`! This document provides instructions for setting up the development environment, contributing code, running tests, and following project conventions.

---

## 1. Development Setup

### Prerequisites
- **Python**: 3.11 or 3.12
- **Git**
- Optional: **Docker** & **Docker Compose**

### Installation

#### Linux / macOS
```bash
# Clone the repository
git clone https://github.com/Ankur377823/hybrid-rag-search.git
cd hybrid-rag-search

# Create and activate virtual environment
python3 -m venv .venv
source .venv/bin/activate

# Install editable package with dev dependencies
pip install --upgrade pip
pip install -e ".[dev]"
```

#### Windows (PowerShell)
```powershell
# Clone the repository
git clone https://github.com/Ankur377823/hybrid-rag-search.git
cd hybrid-rag-search

# Create and activate virtual environment
python -m venv .venv
.venv\Scripts\Activate.ps1

# Install editable package with dev dependencies
pip install --upgrade pip
pip install -e ".[dev]"
```

## 2. Running Quality Checks & Tests

Before submitting a Pull Request, verify that all linting, typing, and test suites pass:

### Linux / macOS (using Makefile)
```bash
make check
```
*(Runs `ruff check`, `ruff format --check`, `mypy src`, and `pytest --cov`)*

### Manual Commands (Cross-Platform)

```bash
# 1. Format and lint checks
ruff check .
ruff format --check .

# 2. Strict static type analysis
mypy src

# 3. Run test suite
pytest -v
```

> [!IMPORTANT]
> The CI test suite enforces **80% minimum test coverage**. PRs that drop coverage below this threshold will not pass quality gates.

## 3. Project Architecture & Standards

### Multi-Tenant Isolation
When adding any new endpoints, database queries, or vector operations:
- Always enforce **tenant scoping by `user_id`**.
- Do not execute raw SQL queries without parameterized placeholders (`$1, $2` for PostgreSQL converted to `?` for SQLite).
- Ensure that candidate chunks returned during retrieval are strictly filtered by `user_id` before reranking or generation.

### Grounded Citations & "I Don't Know"
- Answers generated by the engine must cite source chunks using `[N]` bracketed notation.
- If retrieval confidence falls below `RAG_IDK_RETRIEVAL_THRESHOLD` (default: 0.35), the pipeline must cleanly refuse to answer rather than hallucinate.
- If modifying retrieval or chunking logic, update or add test cases in `eval/golden_qa.jsonl`.

### Testing Principles
- **No real network calls in tests**: Use `httpx.MockTransport` and the `make_llm_client` fixture provided in `tests/conftest.py`.
- Tests must be deterministic and fast.

### Frontend Development
- The Web Studio UI resides in `frontend/`.
- Built with **semantic HTML5**, **vanilla CSS tokens**, and **modular vanilla JavaScript** — avoid adding external heavy UI frameworks or runtime bundlers.
- Ensure all interactive elements have descriptive IDs and accessible tags.

## 4. Git & Commit Conventions

We follow the [Conventional Commits](https://www.conventionalcommits.org/) specification:

- `feat(scope): ...` for new features (e.g. `feat(db): add connection pooling`)
- `fix(scope): ...` for bug fixes (e.g. `fix(retriever): enforce user_id filtering`)
- `docs(scope): ...` for documentation updates
- `test(scope): ...` for adding or updating tests
- `refactor(scope): ...` for internal restructuring

### Pull Request Workflow
1. Fork the repository and create your branch from `main`:
   ```bash
   git checkout -b feat/my-improvement
   ```
2. Write clean, tested code and update documentation where appropriate.
3. Verify all checks pass locally (`pytest`, `mypy`, `ruff`).
4. Commit your changes with descriptive messages and push your branch.
5. Open a Pull Request against `main` on GitHub with a clear summary of changes.

---

## 5. Code of Conduct

Be kind, constructive, and respectful. Disagreements must be about technical trade-offs and code, never about individuals.
